# Décisions durables

Une ligne par décision : date, décision, raison. Ajouter en bas, ne pas réécrire
l'historique (une décision annulée reçoit une nouvelle ligne qui la remplace).

| Date | Décision | Raison |
|---|---|---|
| 2026-11-12 | Python **3.13** épinglé (`.python-version`, `requires-python = ">=3.13,<3.14"`), installé par uv. | Wheels disponibles pour toute la pile (Django 5.2, psycopg, Celery) ; 3.14 encore trop récent pour une partie de l'écosystème. |
| 2026-11-12 | **CSP stricte dans tous les environnements** (`default-src 'none'`, `script-src 'self'`, aucun `unsafe-inline` ni `unsafe-eval`). | Le dev se comporte comme la prod : une violation CSP apparaît dès le développement, pas au déploiement. |
| 2026-11-12 | Cookies de session et CSRF préfixés **`__Host-`** dans `prod.py` uniquement ; noms par défaut en dev. | `__Host-` impose HTTPS, `path=/` et aucun domaine (un sous-domaine ne peut pas écraser le cookie) ; incompatible avec `http://localhost` en dev. |
| 2026-11-12 | `TimeStampedModel.created_by` : FK vers `AUTH_USER_MODEL`, `on_delete=PROTECT`, `null=True` (objets créés par le système), `related_name="+"`. **Un utilisateur ne se supprime pas, il se désactive** (`is_active=False`). | Garder l'auteur de chaque objet pour l'audit et l'archivage ; `PROTECT` lève `ProtectedError` plutôt que d'effacer ou d'orpheliner l'historique. |
| 2026-11-12 | **htmx 2.0.11 vendorisé** dans `static/vendor/htmx/htmx.min.js`, extrait de `https://registry.npmjs.org/htmx.org/-/htmx.org-2.0.11.tgz` (sha512 npm vérifié) ; empreinte `sha384-2OatzQy1H+Zd/IIrjr1TcuDGqLXeHhbooAyJY1KdQMKnr4LZ22k31GBLdYKHmVjg`. | Pas de CDN (CLAUDE.md) ; l'empreinte, recalculée par un test, détecte toute modification du fichier. 2.x stable (4.x encore en `next`). |
| 2026-11-12 | `dev.py` et `test.py` **refusent de démarrer** si `DJANGO_ALLOWED_HOSTS` contient un hôte non local (`config/settings/guards.py`). | Un mauvais `DJANGO_SETTINGS_MODULE` sur un serveur exposerait `DEBUG=True` (page technique révélant `CELERY_BROKER_URL`) et l'admin sans MFA ; l'environnement de prod liste toujours son domaine public, ce qui permet de le détecter. |
| 2026-11-12 | **Tests sur PostgreSQL** (pas SQLite) ; pytest échoue avec un message explicite si la base est injoignable. | M2 repose sur un trigger PostgreSQL et des contraintes propres à PostgreSQL ; tester sur une autre base masquerait des erreurs. |
| 2026-11-12 | **MFA = django-allauth** (`allauth.account` + `allauth.mfa`) : TOTP, WebAuthn (second facteur ; connexion par clé d'accès seule désactivée), codes de récupération. Préféré à django-otp + py_webauthn. | Couvre les trois facteurs, la connexion en deux étapes, la ré-authentification et la limitation des tentatives : ~4 fois moins de code de sécurité à écrire ; WebAuthn dès M1. |
| 2026-11-12 | **Codes de récupération chiffrés, non hachés** : allauth stocke une graine (HMAC → codes) passée par `MFAAdapter.encrypt()`, comme la graine TOTP. `encrypt()` est l'identité en M1, branché sur le coffre en M2 ; un test fait échouer la prod tant que c'est l'identité (`docs/DEPLOYMENT.md`). L'affichage des codes exige une ré-auth récente **avec second facteur**. | La graine TOTP est forcément réversible : hacher les codes n'ajoute presque rien si les deux graines sont chiffrées pareil. |
| 2026-11-12 | **Ré-authentification** : `@recent_auth_required` / `RecentAuthRequiredMixin` (`apps/accounts/reauth.py`), < 10 min, **second facteur exigé par défaut** (`mfa=True`) ; le mot de passe seul n'est accepté qu'avec `mfa=False` écrit explicitement. Les modules dépendent de cette API, pas d'allauth. | Refus par défaut ; changer de bibliothèque ne touche que `reauth.py`. |
| 2026-11-12 | **`Membership` : pas de chevauchement de périodes** pour un même `(user, thesis, role)`, et **au plus un `PHD_STUDENT` actif par thèse**, garantis par des contraintes d'exclusion PostgreSQL sur `tstzrange(active_from, active_until, '[)')` (extension `btree_gist`). Période semi-ouverte ; retrait = `active_until = now()`, jamais de suppression ; changement de rôle = clôture + nouvelle ligne. | Remplace l'« unicité partielle sur `active_until IS NULL` » validée au plan : un `CSI_MEMBER` actif a un `active_until` dans le futur et échapperait à cette contrainte. L'exclusion exprime exactement « unique parmi les lignes actives à tout instant » et garde l'historique. |
| 2026-11-12 | **Droits relus en base à chaque requête** (`roles_of()`), jamais mis en cache dans la session ; `is_superuser` / `is_staff` ne donnent **aucun** droit sur une thèse. | Un membre retiré perd l'accès dès la requête suivante ; pas d'élévation par l'admin Django. |
| 2026-11-12 | **`GUEST` sans aucun droit au niveau de la thèse** en M1 ; ses accès (« une réunion », « projet partagé ») seront des autorisations par objet (M5, M2). | Refus par défaut. |
| 2026-11-12 | **`CSI_MEMBER` à durée limitée** : `active_until` = acceptation de l'invitation + 60 jours, prolongeable par le `PHD_STUDENT` (ré-auth). `CSI_MEMBER` est incompatible avec `PHD_STUDENT`, `DIRECTOR`, `CO_SUPERVISOR`, `INDUSTRIAL_TUTOR` sur une même thèse. | Le CSI intervient ponctuellement et doit rester extérieur à l'encadrement (charte I2S). |
| 2026-11-12 | **Changement d'adresse électronique désactivé** (routes de gestion des courriels d'allauth fermées). | `User.email` et `EmailAddress` d'allauth ne peuvent pas diverger. |
| 2026-11-12 | **Squelette `apps/vault/` créé dès M1** : `crypto.py` (jetons : `secrets.token_urlsafe(32)`, SHA-256, `hmac.compare_digest`) et `services.audit()` (journal en ajout seul, chaînage ajouté en M2). | Règle 1 (seul `vault/crypto.py` importe la cryptographie) ; les appels des autres modules sont définitifs dès M1. |
| 2026-11-12 | **Cache Redis obligatoire en prod** (`CACHES`), testé. | La limitation des tentatives d'allauth vit dans le cache : un cache par processus la rendrait contournable. |
| 2026-11-12 | **Courriels envoyés par une tâche Celery** ; statut d'envoi de l'invitation visible sur la page Équipe. | Le temps de réponse ne révèle pas l'existence d'un compte ; une invitation non partie se voit. |
| 2026-11-12 | **time-machine** (et non freezegun) pour les tests dépendant de l'heure. | Agit au niveau de l'horloge C : couvre aussi `time.time()` et les bibliothèques tierces (allauth, Django). |
| 2026-11-12 | **Prolongation d'un `CSI_MEMBER`** : de 1 à **90 jours** par prolongation (60 par défaut), uniquement si l'appartenance est encore active ; un CSI expiré est réinvité. | L'accès du CSI reste ponctuel ; une réinvitation après expiration repasse par le contrôle d'adresse et le journal. |
| 2026-11-12 | **`AuditEvent` n'hérite pas de `TimeStampedModel`** : il a son propre `timestamp` et aucun `updated_at`. | Une ligne en ajout seul n'est jamais modifiée ; un `updated_at` ferait croire le contraire. |
| 2026-11-12 | **Pseudonymes du journal (`ip_hash`, courriel d'une connexion échouée) = HMAC-SHA256 sous une sous-clé dérivée de `MASTER_KEY`** par HKDF-SHA256 (`info = b"audit-pseudonym-v1"`, sans sel), dans `apps/vault/crypto.py`, avec le but (`ip`, `email`) lié au message. `MASTER_KEY` obligatoire et vérifiée au démarrage en prod (32 octets en base64). Bibliothèque : `cryptography` (HKDF n'existe que sous `hazmat`, appelé tel quel). | Indépendant de `SECRET_KEY` : la changer ne casse pas les corrélations du journal ; un label versionné permet une future dérivation sans perdre l'ancienne. |
| 2026-11-12 | **Jeton d'invitation généré par la tâche Celery** (le courtier ne voit que l'identifiant ; aucune relance automatique, aucun résultat stocké) ; validité de 72 h comptée **à l'envoi**. Parcours GET (lien, sans effet) → POST « Continuer » → `/invitation/accept/`, et `Referrer-Policy: no-referrer` sur la page du lien. | Redis et ses fichiers de persistance ne contiennent jamais de jeton ; avec `SameSite=Strict`, un clic depuis une messagerie n'envoie pas le cookie de session, d'où l'étape POST ; les scanners de liens sont sans effet. |
| 2026-11-12 | **Connexion par allauth** (mot de passe puis second facteur) ; `logout` reste la vue Django en POST seul ; routes allauth fermées (404) : inscription, gestion et vérification des adresses, connexion et ré-authentification par code envoyé par courriel. `ACCOUNT_EMAIL_VERIFICATION = "none"` (l'invitation prouve l'adresse ; `EmailAddress` vérifiée et principale créée à l'acceptation). | Surface d'attaque minimale ; un code envoyé par courriel ne doit jamais remplacer le second facteur. |
| 2026-11-12 | **Second facteur obligatoire** : `MfaRequiredMiddleware` renvoie tout utilisateur connecté sans TOTP ni WebAuthn vers l'enrôlement (les codes de récupération seuls ne comptent pas). Le nouvel inscrit est envoyé directement sur l'activation du TOTP ; le mot de passe qu'il vient de choisir est enregistré comme authentification récente. | allauth demande déjà le facteur à la connexion ; reste le compte fraîchement créé. |
| 2026-11-12 | **Ré-authentification : `reauth.py` compte aussi une connexion récente** (même session, < 10 min) du type exigé, alors qu'allauth ne compte que les ré-authentifications explicites. `mfa=True` exige un passage par le second facteur. C'est le seul module qui lit les enregistrements d'authentification d'allauth (API interne), couvert par des tests sur les vrais flux. | Une connexion avec second facteur est au moins aussi forte qu'une ré-authentification ; un seul point à adapter si allauth change. |
| 2026-11-12 | **Codes de récupération** : affichage, téléchargement et régénération enveloppés par `@recent_auth_required` (second facteur < 10 min) ; allauth n'exige sinon qu'une ré-authentification par mot de passe. | Condition (a) de la validation du plan. |
| 2026-11-12 | **Vues de modification de l'équipe** : ordre des contrôles = droit (`permissions.py`, 403) → ré-auth avec second facteur → service (qui revérifie). La révocation d'une invitation n'exige pas de ré-auth (elle ne fait que retirer un accès possible). | Un rôle non autorisé reçoit 403 sans être invité à se ré-authentifier. |
| 2026-11-12 | **Mise à jour d'allauth = relancer toute la suite et relire `apps/accounts/reauth.py` en priorité.** `reauth.py` lit les enregistrements d'authentification de session d'allauth (`allauth.account.internal.flows.login`), une API interne ; la version est figée par `uv.lock`. | Une évolution silencieuse de cette API pourrait affaiblir la ré-authentification ; les tests passent par les vrais flux et doivent la révéler. |
| 2026-11-12 | **Codes de récupération affichés une seule fois** (`MFA_RECOVERY_CODES_SHOW_ONCE = True`) : après la première consultation, ils ne sont plus ni affichables ni téléchargeables ; seule la régénération (second facteur < 10 min) en donne de nouveaux. | Se rapproche de codes non relisibles : une session volée ne peut pas relire les codes existants. |
| 2026-11-12 | **Écart de temps résiduel accepté sur la réinitialisation du mot de passe** : pour une adresse connue, la mise en file Celery ajoute de l'ordre d'1 ms à la réponse (rien n'est mis en file pour une adresse inconnue). | Négligeable devant la gigue réseau ; la limitation `reset_password` (5/min par adresse) borne de toute façon les mesures. |
